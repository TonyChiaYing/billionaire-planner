# v2.0.0.0 發佈說明、決策紀錄與驗收對照

## 實作決策（推導，非使用者原話；皆可調整）

| 主題 | 決定 | 理由 |
|---|---|---|
| v1 遷移方式 | 不在原 store 上做 SwiftData staged migration，而是：備份 → 只讀備份副本 → 寫入新的 `PlannerV2.store` | v1 原檔永不被寫入，失敗零風險；退回 v1 時資料仍在；以 legacy UUID 達成冪等 |
| 關聯 | 所有關聯用穩定 UUID 欄位，不用 SwiftData relationship | 不用標題當鍵；避免 cascade delete；歷史以封存保留 |
| 容量門檻 | 寬鬆 ≤70%、可行 ≤85%、偏滿 ≤100%、過載 >100%；緩衝 20%（至少 15 分）；休息底線 30 分（一天可用 ≥4 小時才檢查）；切換 >6 次或高耗能 >3 項升為偏滿 | 參考 skill 的建議基準，集中在 `CapacityPolicy` |
| 估時建議 | ≥3 筆相似完成紀錄（同目標，或同類型且標題字元二元組相似度 ≥0.3）的中位數，取 5 分倍數；顯示筆數與範圍 | 中文無空白分詞，用二元組比較 |
| 落後訊號 | 連續 2 個有安排的 7 天週期無成果、7 天內延後 ≥3 次、預測超過期限 >7 天、近 14 天 ≥5 天過載、最近兩次日結都標記受阻；至少兩類才提示 | PRD 7.9 |
| 介入冷卻 | 每日同一問題同一規劃日一次；每週 7 天一次；期限只在風險升級或延後到期；關閉後冷卻 14 天 | product-rules 基準 |
| 版號 | 四段 `2.0.0.0` 存在 CFBundleVersion；`MARKETING_VERSION` 只能三段，設為 `2.0.0` | Apple 限制 |
| 未估時 | 容量計算以 30 分計，並在畫面上標示「未估時」 | 不假裝精準 |

## 已知限制與後續項目（未以空殼入口冒充完成）

- **未做自動化 UI 測試／截圖比對**（PRD 13 的 UI tests、snapshot）；核心流程以 Application 層測試覆蓋，畫面為人工檢查。
- **效能基線未正式記錄**：遷移映射有 1,000 目標／5,000 時間塊測試；20,000 行動的首頁互動尚未在實機量測。
- **真實 v1 資料的 dry-run**：遷移只讀「備份副本」且不寫入 v1 原檔，首次開啟就是在副本上執行；如需在獨立位置先演練，可把 `Backups/` 內的副本交給測試。
- **VoiceOver／鍵盤**：所有動作都有按鈕或選單路徑（不依賴拖放），但尚未以 VoiceOver 實際走過全部流程。
- **iOS 實機**：iOS 版已通過雲端編譯，安裝到 iPhone 需要你的 Apple ID 簽署。
- 「降低本週頻率」恢復方案目前只記錄決定與原因，不自動改動計畫（符合「建議不得靜默改動承諾」）。
- 時區：規劃日以「本地年月日」儲存並記錄時區識別；跨時區旅行時以裝置目前時區解讀時段。

## 回復方式

- 想回到 v1：`bash version.sh restore 1.0.0`。v1 會讀到升級前的原始 `Planner.store`（v2 從未寫入它）。
- v2 自己的資料在 `PlannerV2.store`；可隨時用「設定 → 匯出全部資料（JSON）」備份。
